# Agent 长期记忆系统 - 产品文档

> **文档定位**：面向使用 TogoSpace 的操作者（Operator）及 Agent 编排人员，聚焦**用户痛点、产品交互体验、核心业务规则与实际预期效果**。  
> **关联文档**：[技术设计 (step2_technical.md)](./step2_technical.md)

---

## 1. 背景与用户痛点

在 TogoSpace 多 Agent 协作系统中，人类操作者（Operator）与多个 Agent、以及 Agent 之间通过不同的聊天室（房间）进行复杂的任务协同。随着团队运行时间的拉长，用户面临以下三大典型痛点：

1. **“交代过的话，聊几句就忘了”**：
   用户向某个 Agent 提出了明确的工作偏好（例如“方案设计必须先给结论再展开细节”或“写代码必须使用 Python 类型注解”），但在经过多轮对话或触发会话压缩（Compact）后，Agent 很快将这些约定遗忘，迫使人类必须在各个房间反复重复交代。
2. **缺乏沉淀，犯过的错误反复犯**：
   项目推进中踩过的坑、确认的技术决策（如“第一版接口不引入向量数据库，只使用轻量方案”）没有属于 Agent 的长期“笔记本”。换一个房间或过几天开启新任务，Agent 往往又做出已被否决的错误提议。
3. **“要么全背下来，要么全忘光”**：
   以往若强行把所有历史背景都塞入提示词，会导致聊天室里充斥大量重复文字，不仅上下文极速被吃光、Token 成本翻倍，而且 Agent 会因为注意力涣散导致指令遵循率急剧下降。

## 2. 产品目标与预期效果

我们希望为每个 Agent 赋予一个**数字化、结构化的个人“记忆库”**。Agent 能够像专业的团队成员一样，主动记录关键规则、分层管理认知，并在需要时精准提取。

### 2.1 预期的产品效果

* **一次交代，长期遵守**：
  用户在任意房间告知 Agent 的高频偏好与硬性规则，Agent 能将其标记为核心认知。无论会话持续多久、是否经历多次历史压缩，Agent 都能持续稳定遵循。
* **分层认知：核心随时牢记，细节翻书查阅**：
  * **核心铁律（星标）**：与当前工作息息相关的关键规则（如语言偏好、回答格式），Agent 始终牢记在心，无需用户提醒；
  * **日常笔记（普通记忆）**：偶发的经验、历史方案背景，Agent 存入记忆库，只有在遇到相关问题时才“翻书查阅”，绝不给日常对话增加多余噪音。
* **精准查阅，杜绝对话污染**：
  Agent 在查阅过往记忆时，在后台以“概要 + 命中关键片段”的形式精准检索，只在确实需要时才看全文，检索过程完全静默，不会往聊天室倾倒垃圾文本。
* **低成本、低延迟**：
  长期记忆机制不会降低聊天室的响应速度，更不会导致会话中途出现突然的 Token 暴增。
* **记忆透明可控**：
  * **可视化只读查阅**：在 Agent 个人卡片弹窗（Agent Status Card）中新增 **「记忆」Tab**，操作者可直观查看该 Agent 当前所有的星标记忆、普通记忆与已归档记忆（含标题、星标级别、概要及展开查看完整正文），无需支持手动表单编辑；
  * **对话式纠偏与管理**：当操作者发现某条记忆有误或已过时，可在聊天室中通过自然语言随时要求 Agent 修正或归档，真正做到“看得清、管得住”。

### 2.2 本期范围与非目标（Non-Goals）

* **本期包含**：
  * 单 Agent 级结构化长期记忆存储（L1 目录 / L2 概要与片段检索 / L3 正文调阅）；
  * 星标分级注入机制（`summary` / `title` / `none`）与星标配额刚性约束；
  * 供 Agent 自主管理的 5 个记忆工具（列表、读取、搜索、创建、更新/归档）；
  * **Web 前端 Agent 个人卡片页「记忆」Tab（只读查看）** 及配套的后端查询接口；
  * 与会话压缩（Compact）、Agent 重启恢复、以及团队/Agent 数据重置（Clear Data）的完整生命周期联动。
* **本期不包含（后续迭代）**：
  * 前端仅提供只读查看能力，**不支持在前端界面直接新建、编辑或删除记忆**（记忆维护统一由 Agent 自治或通过对话指令驱动）；
  * 暂不引入向量数据库（Embedding）检索，首期采用轻量级多关键词权重与上下文片段匹配；
  * 暂不提供跨 Agent 共享的团队公共记忆库（记忆严格归属单 Agent 私有）。

## 3. 核心功能与概念模型

长期记忆系统围绕 **“单主题槽位”** 与 **“三层信息渐进展开”** 构建。

### 3.1 槽位与记忆形态

* **一个槽位对应一个独立主题**：
  Agent 的记忆不是无序的流水账，而是一条条短小精悍的知识槽位（如“用户回答偏好”、“订单取消时间规范”）。每个槽位包含：
  * **唯一主题标题（`title`）**：80 字符以内，单行概括核心主题；同一 Agent 活跃记忆下标题唯一，禁止同名重复建槽。
  * **单句结论概要（`summary`）**：120 字符以内，单行直截了当给出核心结论与适用条件。
  * **可执行正文（`content`）**：1000 字符以内，记录必要的原因、完整规则或具体参数。更新正文时必须同步更新概要，确保表里一致。
* **记忆自治原则**：
  由 Agent 自己在交互中判断哪些信息具有长期价值，自主执行创建、修正、加星与归档，无需人类手动在后台填表。

### 3.2 三层认知展开模型（L1 / L2 / L3）

为了平衡“Agent 见多识广”与“上下文成本受控”，记忆分为三层渐进暴露：

```text
┌──────────────────────────────────────────────────────────────┐
│ L1：目录层（ID + Title + StarLevel + Tags）                  │
│ 作用：让 Agent 知道自己“记过哪些主题”及其星标状态。             │
│ 成本：极低（仅编号、标题与标签）。                             │
├──────────────────────────────────────────────────────────────┤
│ L2：候选层（Summary + 命中片段 Snippet）                       │
│ 作用：检索时快速判断“这条记忆是否命中当前问题”，直接看到核心结论。 │
│ 成本：低（单句结论 + 前后关键语句预览）。                        │
├──────────────────────────────────────────────────────────────┤
│ L3：正文层（Content 完整详情）                                │
│ 作用：在确实需要具体执行依据、完整步骤时才调阅。                 │
│ 成本：相对最高（完整正文，严格需 Agent 显式查阅）。             │
└──────────────────────────────────────────────────────────────┘
```

> **产品铁律**：正文（L3）永远不会自动注入给 Agent，必须由 Agent 自主判断有必要时才显式查阅，从机制上杜绝长篇大论拖垮模型。

### 3.3 星标机制与黄金预算

并非所有记忆都值得每轮牢记。系统将记忆划分为三种重要度：

| 星标级别 | 产品表现 | 适用内容示例 | Agent 槽位预算 |
|---|---|---|---|
| **概要级星标 (`summary`)** | **极高关注**：记忆 ID、标题与核心结论始终浮现在 Agent 脑海中 | “方案回答先给结论”、“代码必须包含类型声明” | 最多 **6 条** |
| **标题级星标 (`title`)** | **中度关注**：Agent 始终知道该主题与 ID 存在，需要细节再查 | “当前大版本推进目标”、“存储选型核心决策” | 与概要级合计最多 **12 条** |
| **普通未加星 (`none`)** | **背景资料**：平时不进入脑海，遇到相关问题时才搜索发现 | 历史项目复盘、某次偶发 Bug 的排障经验、历史接口配置 | 无数量限制 |

**严格的星标预算机制**：
星标是昂贵的黄金资源，单 Agent 总星标不得超过 12 条（其中概要级至多 6 条）。一旦达到上限，Agent 必须在取消失效星标或合并同类项后才能为新记忆加星，确保 Agent 始终保持清醒聚焦。

### 3.4 记忆生命周期与清理联动

* **持久保留**：在日常运行中，无论是切换聊天房间、触发会话上下文压缩（Compact），还是重启后端服务，Agent 的长期记忆均持久保留。
* **清理联动**：当操作者在界面或接口主动执行“清除 Agent 历史数据”或“清空团队运行数据”时，系统会同步清空对应 Agent 或团队的长期记忆，保证重置后的 Agent 彻底回归初始状态，不残留旧项目的脏规则。

## 4. 用户交互与应用场景

### 场景一：用户提出硬性偏好，跨轮次与压缩后持续生效

* **用户行为**：
  在私聊房间对 Agent 说：“以后的技术方案设计，先给出最终选型结论和权衡，再展开具体实现。”
* **Agent 反应**：
  1. Agent 识别出这是一条跨任务长期有效的用户偏好；
  2. Agent 在后台建立记忆槽位，由于该偏好直接影响每一次方案输出，Agent 主动将其设为**概要级星标**；
  3. 记忆在后台安全落库，Agent 回复用户：“收到，已牢记该偏好，后续方案均优先给出结论与权衡。”
* **后续效果**：
  * 对话持续数十轮后，历史对话达到上限并触发了上下文压缩（Compact）；
  * 用户在另一个任务房间要求设计某个模块，Agent 依然严格遵守“先结论、后细节”的原则输出，**彻底解决多轮遗忘问题**。

### 场景二：历史经验按需查阅，带片段预览秒级确认

* **用户行为**：
  用户向 Agent 询问：“我们团队之前关于订单自动取消的超时阈值是怎么约定的？”
* **Agent 反应**：
  1. 该项决策作为普通记忆沉淀在库中，未被加星（平时不占用提示词）；
  2. Agent 在后台发起针对“订单 超时取消”的多关键词检索；
  3. 检索结果不仅返回了概要，还直接带出了命中正文的关键片段（Snippet）：
     > `…普通订单超时 30 分钟自动关闭；大促期间为避免库存锁定，超时取消时间统一调整为 15 分钟…`
  4. Agent 无需再耗费一次操作去调阅千字正文，直接根据命中的关键片段准确回答用户：“我们约定的普通订单超时取消为 30 分钟，大促期间为 15 分钟。”
  5. 整个检索过程纯粹在后台静默完成，聊天室界面没有任何多余的中间碎片。

### 场景三：过时决策主动归档与更正

* **用户行为**：
  用户告知 Agent：“上周讨论的旧数据库迁移方案废弃了，我们改用新的方案 B。”
* **Agent 反应**：
  1. Agent 通过星标清单中的 ID 或搜索定位到旧方案对应的记忆槽位；
  2. Agent 主动将旧记忆更新为 `archived`（归档状态），或者直接在原槽位上同步更新最新概要与正文；
  3. 归档后的记忆自动剥离星标，未来不再干扰 Agent 的日常工作，同时保证历史痕迹可被回溯。

## 5. Agent 行为准则与边界

为防止 Agent 滥用记忆系统，系统为 Agent 设定了严格的行为准则：

1. **应该记什么**：
   * 用户明确要求的个人习惯与交付风格；
   * 团队已确认的技术架构决策、技术栈规范；
   * 当前项目正在攻坚的核心目标与不可逾越的边界约束；
   * 经过实测验证、后续可能多次复用的关键操作步骤。
2. **绝对不能记什么**：
   * 临时闲聊与无意义寒暄；
   * 敏感信息（用户密码、私钥、Token、个人隐私等）；
   * Agent 未经证实的推测与假设；
   * 仅对当前一句话有效的超短期信息。
3. **维护优于新建**：
   * 发现同一主题有新变化时，优先在原记忆上更新，严禁针对同一概念重复建立多个槽位。
4. **及时降级与归档**：
   * 临时项目完结、版本上线或信息失效后，必须及时取消星标或将其归档。

## 6. 验收标准（用户体验视角）

| 验收项 | 期望用户体验 | 验证方法 |
|---|---|---|
| **长期记忆生效** | 用户告知偏好后，在后续会话、其他房间、甚至多次上下文压缩后，Agent 依然严格遵守。 | 在房间 A 交代格式偏好，推动多轮对话触发 Compact 后，在房间 B 检查 Agent 回复是否依然遵循。 |
| **检索精准与无扰** | 询问历史未加星问题时，Agent 能通过多关键词准确检索回答，且聊天界面无多余无关内容倾倒。 | 询问过去记录过但未星标的配置，检查 Agent 回复准确性及工具调用的静默流畅度。 |
| **星标预算受控** | Agent 不会随心所欲无节制加星，始终将星标控制在 12 条（概要级 6 条）以内。 | 连续给 Agent 灌输多条重要规则，检查配额拦截及 Agent 是否懂得合并或取消低频星标。 |
| **卡片页可视查阅** | 打开 Agent 个人卡片切换到「记忆」Tab，可清晰查看该 Agent 的星标记忆、普通记忆及归档记忆详情。 | 在前端点击 Agent 卡片打开详情弹窗，切换至「记忆」Tab，检查星标标识、概要及展开正文的展示是否准确。 |
| **记忆随时可纠偏** | 用户指出某项记忆已失效或要求更新时，Agent 能精准修改旧条目，不再复读旧结论。 | 明确纠正既往认知，核实「记忆」Tab 中的内容变化及后续轮次 Agent 是否采用新结论。 |
| **性能与成本稳定** | 启用长期记忆后，聊天室的吐字延迟、首字响应时间与 Token 消耗保持平稳无异动。 | 对比记录前后的单轮消耗，确认同一 Session 内未出现因记忆写入导致的 Prompt Cache 失效。 |
