# Docker 执行环境 - 产品文档

> 关联文档：[技术设计](./step2_technical.md)

## 1. 背景与目标

现在 Agent 的文件读写、命令执行都直接跑在宿主机上，会带来四类问题：装依赖污染宿主环境、危险命令打到真实路径、Agent 之间互相干扰、任务无法复现。

本功能给 Agent 提供两块彼此独立的能力：

- **容器管理**：创建 / 删除 / 查看「自己造的」容器；
- **容器访问**：进入任意已存在的容器执行工具，或退出回宿主。

拆开的目的：宿主上已有的容器（运维起的、带 GPU / 数据库 / 内网访问的）不必由本系统创建，Agent 也能进去用。

## 2. 工具一览

| 工具 | 作用 | 要点 |
|---|---|---|
| `create_container(image?)` | 创建容器 | 自动挂载个人目录与共享目录；**只创建，不切换执行环境**；返回 `container_id` 与容器名 |
| `delete_container(container_id \| record_id)` | 删除容器 | 只能删自己创建的；普通容器传 `container_id`，预记录传 `record_id`（二选一）；正在使用的不能删，需先 `exit_to_host` |
| `list_containers()` | 查看容器 | 返回当前执行环境 + **自己创建的**容器及状态（含创建中的预记录，返回 `record_id` 与可能为空的 `container_id`，按容器名展示），不枚举其他容器 |
| `enter_container(container_id)` | 进入容器 | 传目标容器 `container_id`；不校验属主、不做挂载；**外部容器须为运行状态（非运行状态需 Agent 自行启动 / 恢复）**；不接受镜像名 |
| `exit_to_host()` | 退出回宿主 | 宿主环境恢复原样，容器状态按 §4.1 规则收敛 |

系统不做任何自动切换：Agent 默认在宿主，只有主动调用 `enter_container` 才进容器。

所有工具中的 `container_id` 均为 Docker 容器 12 位短 ID（完整 ID 前 12 位），不使用容器名。`delete_container` 另支持 `record_id`（容器记录 ID），用于尚无 Docker ID 的预记录。

## 3. 容器管理

### 3.1 自动挂载（仅 `create_container` 创建的容器）

| 宿主目录 | 容器内路径 | 权限 |
|---|---|---|
| 个人工作目录 | `/workspace/self` | 读写，双向实时可见 |
| 团队共享目录 | `/workspace/team_shared` | 只读，写入会被拒绝并提示原因 |

删除容器不影响这两个目录的文件。其他来源的容器（外部容器、Agent 自己 `docker run` 的）一律不挂载。

### 3.2 镜像

- `image` 默认 `ubuntu:24.04`：自带 `bash` / coreutils，开箱可用，体积约 78MB。默认值只体现在参数上，不做成系统配置项。
- 镜像必须**已在本地存在**，不自动拉取；缺失时提示先 `docker pull`。
- 镜像里**必须有 `bash`** 才能用 `execute_bash`（如 `alpine` 没有）。此时文件工具正常，`execute_bash` 会明确提示「镜像内没有 bash」，并给出出路：换镜像，或在容器内装 bash。系统不会偷偷用 `sh` 代替。
- 镜像内需有可写的 `/tmp`：系统将 gtsp 注入 `/tmp/gtsp`。`/tmp` 不存在或不可写时，创建 / 进入直接失败并提示具体原因，需换镜像或自行准备 `/tmp`；本版不自动补齐。

### 3.3 命名与配额

- 容器名：`agent-t<team_id>-<agent名>-<1..3>`，如 `agent-t2-xiaomage-1`。Agent 名含 Docker 不允许的字符（中文、空格、emoji 等）时回退为 `agent-t<team_id>-<agent_id>-<1..3>`，保证不会因名字创建失败。
  > 依据 Operator 2026-11-01 指令修订（原规则 `agent-<agent名>-<1..3>`）：容器名在未删除范围内全局唯一，不带 team 段时两个团队各自都有同名 Agent（如都叫「小美」）会导致第二个永远建不出容器。team 段用 **`team_id`（数字）而非团队名**——「ToGo开发部」与「ToGo研究部」经字符规范化后都是 `togo`，用团队名等于没修。
- 每个 Agent 最多 3 个自己创建的容器（含已停止的）；满了提示先删除。外部容器不占配额。

## 4. 容器访问

### 4.1 进入与退出状态规则

| 容器类型与进入前状态 | 进入时系统处理 | 退出后状态 |
|---|---|---|
| **自建容器**（进入前 `created` / `exited`） | 系统拉起（gtsp 为主进程，`--init` 的 tini 为 PID 1） | 关 stdin 自然停回 `exited`（已停止） |
| **外部 / 他人容器（运行中）** | 直接借用（`exec` 注入 gtsp） | 继续运行（不影响原主进程） |
| **外部 / 他人容器（非运行状态）** | **不支持直接进入**，报错并提示「该容器未运行（实际状态 xxx），请先自行启动 / 恢复」 | — |

**例外**：自己创建的容器空闲时应为 `created` 或 `exited`（已停止）。若进入时发现它在 `running`，说明有异常残留，系统**直接报错，不替你停**，由 Agent 自行 `docker stop` 后重试，或删掉重建。若处于 `paused` / `dead` / `restarting` / `removing` 等其他异常状态，统一按进入失败处理并提示实际状态，系统不自动恢复。

### 4.2 其他规则

- **工作目录**：进入后沿用容器自身的工作目录（镜像 `WORKDIR`，为空则 `/`），系统不改写。默认镜像进入后是 `/`，需要时自行 `cd /workspace/self`。
- **同一时刻只在一个容器内**：从 A 直接进 B 时，先按规则退出 A。
- **工具范围**：在容器内时，文件读写、命令执行、进程管理类工具在容器内执行；发言、任务、团队管理类工具仍在宿主，权限不变。
- **后台进程不跨环境**：切换环境时，上一环境中 Agent 启动的后台进程随之结束。
- **重启不恢复**：后端重启后 Agent 一律回到宿主；容器记录保留，不残留运行中的自建容器。
- 要换镜像请用 `create_container(image=...)`，不要给 `enter_container` 传镜像名。

## 5. 依赖安装落点

- 项目内产物（`node_modules`、`.venv`、构建产物）写在 `/workspace/self` 下 → 真实落在宿主个人目录，删容器不丢。
- 全局安装（`npm -g`、`apt install`、系统级 `pip`）只在容器层 → 删容器即消失，宿主不受影响。
- 外部容器没有个人目录映射，写入不会回到宿主（除非该容器自己挂了宿主路径），需手动搬运。

## 6. 异常与可见性

- 五类异常各有独立可读提示：Docker 未运行、镜像缺失、容器已被外部删除、进入超时、容器不可执行。
- Docker 不可用时只有容器工具报错，宿主上的全部现有能力不受影响。
- Agent、Web 界面、活动记录都能看到「当前在宿主还是哪个容器」及自建容器列表；不展示宿主上的其他容器。

## 7. 示例

```text
小马哥: create_container()
        → 返回 container_id: "7b1a2c3d4e5f"（agent-t2-xiaomage-1 已创建，仍在宿主）
        enter_container(container_id="7b1a2c3d4e5f")
        → 进入，工作目录 /
        execute_bash "cd /workspace/self/proj && npm install && npm run lint"
        exit_to_host()
        → 回宿主，容器停回已停止

阿张:   enter_container(container_id="a8b9c0d1e2f3")
        → 进入已在运行的外部容器，提示「未挂载个人目录」
        execute_bash "mysql --version"
        exit_to_host()
        → 回宿主，外部容器原主进程保持运行

小杰:   enter_container(container_id="f1e2d3c4b5a6")
        → 报错：该自建容器处于运行状态（正常应为已停止），可 docker stop 后重试或删除重建
```

> 示例中的容器名为 `agent-t2-xiaomage-1`，依据 Operator 2026-11-01 指令修订（原文为 `agent-xiaomage-1`），详见 §3.3。

## 8. 范围

**本次不做**：自动切换执行环境、启动时自动进容器、属主校验与准入白名单、自动拉起或恢复非运行的外部容器（需 Agent 自行处理）、自动 pull 镜像、跨 Agent 编排、容器内 GUI、细粒度网络策略（只有有网 / 无网两档）、一次性任务容器、TUI 展示。

**已知风险（本版接受）**：进入外部容器会继承它的全部可见面（环境变量、挂载的宿主路径）。若它挂了 `docker.sock` 或宿主根目录，Agent 也能看到。本版不检测、不拦截。

## 9. 验收标准

**管理**
- [ ] `create_container` 只创建不切换，自动挂载两个目录，返回 `container_id` 与容器名。
- [ ] 中文等非法 Agent 名回退为 `agent-t<team_id>-<agent_id>-<1..3>`，不会创建失败。
  > 依据 Operator 2026-11-01 指令修订（原文为 `agent-<agent_id>-<1..3>`）。
- [ ] 两个不同团队的同名 Agent 各自都能建出容器，容器名不同（team 段用 `team_id` 区分）。
- [ ] 不传 `image` 时为 Ubuntu 24.04；传自定义镜像则使用之；本地不存在时报错并提示 `docker pull`。
- [ ] 无 bash 镜像（如 `alpine:3.19`）能建、能进、文件工具可用，`execute_bash` 返回明确原因与出路。
- [ ] 最多 3 个自建容器；外部容器不计入，也不出现在 `list_containers`。
- [ ] `delete_container` 只能删自己的；支持 `container_id` / `record_id` 二选一；删除正在使用的容器被拒绝；删除后个人目录文件完整。

**访问**
- [ ] 自建容器：容器内写文件宿主可见；退出后停回 `exited`（已停止）；再次进入仍是同一容器，已装依赖还在。
- [ ] 自建容器处于运行中时进入，返回明确错误与两条出路，且容器状态未被改动。
- [ ] 自建容器处于 `paused` / `dead` / `restarting` 等异常状态时进入失败，提示实际状态，系统不自动恢复。
- [ ] 外部容器（含 Agent 自己 `docker run` 的）在运行中时可进入，并收到「未挂载个人目录」提示；退出后容器仍运行。
- [ ] 外部容器处于非运行状态（停止 / 暂停等）时调用 `enter_container` 被拒绝，提示先自行启动或恢复。
- [ ] 进入后工作目录等于容器的 `WORKDIR`（为空则 `/`）。
- [ ] `enter_container` 传镜像名被拒绝，并提示用 `create_container(image=...)`。
- [ ] 同一时刻只进入一个容器；宿主 ↔ 容器来回切换 ≥3 次无状态错乱、无残留进程。
- [ ] 切换环境后，工具执行位置符合 §4.2；上一环境的后台进程被清理。

**异常与稳定性**
- [ ] 五类异常各有独立可读提示；外部删除容器后下一次工具调用即收到提示，而非超时。
- [ ] Docker 不可用时，宿主现有能力不受影响。
- [ ] 后端重启后回到宿主，容器记录保留，不残留运行中的自建容器。
- [ ] 未使用容器的 Agent 行为零变化，全量测试基线不下降。
