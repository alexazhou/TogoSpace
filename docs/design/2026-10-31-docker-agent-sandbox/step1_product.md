# Docker 执行环境 - 产品文档

> **文档定位**：面向使用与维护本功能的产品、测试与使用者，聚焦**外部可观察的系统行为、业务规则与工具用法**。
> **关联文档**：[技术设计 (step2_technical.md)](./step2_technical.md)

---

## 1. 目标与背景

给 Agent 提供两块彼此独立的能力：**容器管理**（创建 / 删除 / 查看容器）与**容器访问**（进入某个容器执行 / 退出回宿主）。

拆成两块的核心目的，是让**容器不必由本系统创建也能使用**。宿主机上已经存在的容器（运维手工起的、带 GPU 的、带数据库或内网访问的），Agent 同样可以进去干活。管理能力管的是「我造的机器」，访问能力管的是「我能用哪些机器」。

### 要解决的问题

当前 Agent 的文件读写与命令执行直接跑在宿主机上（现有 28 个 Agent 均如此，每一次 `read_file` / `execute_bash` 都打在宿主机）。由此带来四类问题：

1. Agent 装依赖会污染宿主全局环境；
2. 跑危险命令会打到真实路径；
3. 两个 Agent 之间会互相踩；
4. 任务无法复现。

容器提供一台「用完即弃」的机器：个人工作目录挂载进去，装什么都留在容器里，宿主环境干净；危险操作打不到真实路径；删掉容器，文件还在。

## 2. 能力一：容器管理

管的是「归属自己的资源」。

| 工具 | 作用 | 行为要点 |
|---|---|---|
| `create_container` | 创建容器 | **自动挂载**个人目录与团队共享目录，返回 `container_id` 与可读容器名。**只准备环境，不切换执行环境** |
| `delete_container` | 删除容器 | 只能删除自己创建的容器；**正在使用的容器不允许删除**，会报错要求先退出 |
| `list_containers` | 查看容器 | 返回「当前执行环境」+「**自己创建的容器列表**」，含每个容器的状态。不返回其他容器 |

### 2.1 创建容器时自动挂载目录（仅对自己创建的容器有效）

**自动挂载是容器管理的能力，只对 `create_container` 创建的容器生效。** 其余所有容器——宿主机上已存在的容器、Agent 自己 `docker run` 起的容器——都不会被自动挂载，Agent 进去看到的是它原本的目录视图。

自己创建的容器自动挂载两个目录：

- 个人目录映射为 `/workspace/self`，也就是宿主的个人工作目录。容器内写的文件，宿主上立刻可见；宿主上改的文件，容器内立刻可见。删除容器不影响任何文件。
- 团队共享目录映射为 `/workspace/team_shared`，容器内可读，默认不可写。写入会被拒绝并说明原因与替代做法。

### 2.2 容器命名

容器名为 `agent-<agent名>-<序号>`，例如 `agent-小马哥-1`。在宿主机的容器列表里一眼能看出是哪个 Agent 的容器。

### 2.3 镜像

- 默认镜像为 **`ubuntu:24.04`**。
  - 选它的原因：gtsp 二进制放入容器内运行，对镜像 glibc 有要求。`ubuntu:24.04` 的 glibc 为 2.39，是各主流基础镜像中最宽松的一档，不会因 glibc 过旧导致工具起不来。
  - 体积代价可接受：约 78MB（压缩后约 30MB），与 `debian:bookworm-slim` 的约 75MB 只差约 3MB，不值得为此换更「精简」的镜像。
  - 明确排除低版本：`ubuntu:20.04`、`debian:bullseye` 的 glibc 为 2.31，`alpine` 使用 musl，这三类镜像不作为默认镜像。
- `create_container` **不开放 `image` 参数**，一律使用上面这个内置的默认镜像。
- **默认镜像不做成系统配置项**，先固定写在代码里，避免一开始就引入配置面。
- 需要别的镜像时走容器访问：Agent 用 `execute_bash` 自己 `docker run` 起容器，再 `enter_container` 进去。镜像的灵活性由这条路径提供，不需要在 `create_container` 上开参数。

### 2.4 删除容器

- 只能删除自己创建的容器。
- **正在使用的容器不允许删除**：报错并提示「请先调用 `exit_to_host` 退出该容器，再删除」。
- 删除后容器从自己的容器列表中消失；容器内装好的环境随之消失。
- 个人目录与共享目录的文件不受影响（它们是宿主上的真实目录）。

## 3. 能力二：容器访问

管的是「我现在在哪执行」。系统不做任何自动切换——Agent 默认在宿主机上工作，只有它主动调用 `enter_container` 才进容器。

| 工具 | 作用 | 行为要点 |
|---|---|---|
| `enter_container` | 进入 | 目标**必须是已存在的容器**（`container_id` / 容器名）。**不校验属主**：自己的、别人创建的、手工起的容器都可以进。**不做任何挂载** |
| `exit_to_host` | 退出回宿主 | 宿主执行环境恢复原样；当前容器的运行状态按「进入前状态」规则处理 |

**只接受容器，不接受镜像。** 想用某个镜像，Agent 先在宿主机上用 `execute_bash` 执行 `docker run` 自己起一个容器，再 `enter_container` 进去。起容器是通用能力，不需要做成工具。

### 3.1 进入与退出不影响容器的运行状态

复用这个容器，状态保留，可反复进出：

- 进入前容器**在运行** → 退出后容器**继续运行**，其内部状态不被打断（只是借用它的执行能力，不改变它的运行状态）。
- 进入前容器**已停止** → 我们先把它拉起来，退出后**停回停止状态**（谁启动谁负责停）。

### 3.2 两块能力的关系

- **管理不依赖访问**：可以只创建不进入，也可以只进入一个已存在的容器。
- **访问不产生归属**：进入一个已存在的容器不改变它的属主，也不占用自己的容器配额。
- **访问不做挂载**：自动挂载只在 `create_container` 创建容器时发生。
- **配额只算 `create_container` 创建的容器**：同一 Agent 最多 3 个（含已停止的）。用 `docker run` 自己起的容器不计入本系统配额。

## 4. 其他功能特性

### 4.1 执行环境是运行中可拨的开关

切到容器后，文件读写、命令执行、进程管理类工具都在容器内执行；发言、任务、团队管理类工具不受影响，仍在宿主后端，权限与门禁不变。随时可切回宿主，切回后与从未进过容器完全一致。

### 4.2 多容器并存，同一时刻只进入一个

可以建多个容器，但一个 Agent 同一时刻只在一个容器内；从 A 容器直接进 B 容器时，先按规则退出 A。

### 4.3 环境异常可读，且优雅降级

Docker 未运行、镜像缺失、容器已被外部删除、进入超时、容器不可执行，五种情况各有独立且可读的提示，不是笼统的「工具调用失败」。Docker 不可用时容器工具报明确原因，Agent 在宿主机上的全部现有能力不受影响。

### 4.4 状态可见

Agent 自己、Web 界面、活动记录都能看到「当前在宿主还是哪个容器」，以及自己创建的容器列表与状态（运行中 / 已停止）。

不展示、也不枚举宿主机上其他容器的信息——其他容器只能由 Agent 明确指名进入（`enter_container`），打听不到全貌。

## 5. 效果演示

### 自己造机器装依赖

```
小马哥: 需要在项目里跑一遍 lint，得装几个 npm 依赖。
        （create_container → 容器已创建，container_id=abc123，
          个人目录映射到 /workspace/self，当前执行环境仍为宿主）
        （enter_container("abc123") → 当前执行环境=容器）
        （execute_bash "cd /workspace/self/myproj && npm install && npm run lint"）
小马哥: lint 跑完了，3 个告警都修好了。依赖装在容器里，宿主 node 环境没动。
        （exit_to_host() → 当前执行环境=宿主；容器 abc123 停回停止状态）
```

### 想用某个镜像，自己起一个容器再进

```
小美: 想试一段 Python 3.11 的脚本，本机 Python 版本不对。
      （execute_bash "docker run -d --name py311 python:3.11-bookworm sleep infinity"
        → 容器 py311 已在宿主机上起好）
      （enter_container("py311") → 当前执行环境=容器；
        该容器不是本系统创建的，没有自动挂载，容器内文件不随退出回宿主）
      （execute_bash "python3.11 --version"）
小美: 跑通了。
      （exit_to_host() → 当前执行环境=宿主；py311 仍在运行）

小美: 但脚本在我个人目录里，容器里看不到。
      → 那里用 create_container 建一个会自动挂载个人目录的容器更合适。
```

要点：**起容器是通用能力，用 `execute_bash` 就够了**；`enter_container` 只负责"进去用"，不管容器怎么来的。

### 借用已有的机器

```
阿张: 要连内网数据库复现问题，已经知道运维起的那个叫 mysql-test，直接进。
      （list_containers() → 只有空列表：自己没建过容器。
        其他容器不会出现在这里，但知道名字仍然可以进）
      （enter_container("mysql-test") → 已进入；该容器未挂载你的个人目录，
        容器内文件不随退出回宿主，需要时请手动搬运到个人目录）
      （execute_bash "mysql -h 127.0.0.1 -uroot -e 'show databases'"）
阿张: 连上了，问题出在索引上。
      （exit_to_host() → 当前执行环境=宿主；mysql-test 仍在运行）
```

### 进一台已停止的容器

```
小杰: 昨天那台还剩着，接着用。
      （enter_container("abc123") → 容器原为停止状态，已拉起并进入）
      （exit_to_host() → 当前执行环境=宿主；容器 abc123 已停回停止状态）
```

### 容器被外部清理

```
阿张: （execute_bash "ls /workspace/self"）
      → 执行环境不可用：容器 abc123 已不存在（可能被外部删除），
        你的个人目录文件仍在宿主上，未受影响。
        请调用 create_container 重新创建，再 enter_container 进入。
```

### 容器数量达到上限

```
小马哥: （create_container，当前已有 3 个自己创建的容器）
      → 容器数量已达上限（3/3）。请先调用 delete_container
        删除不再需要的容器，再创建新的容器。
```

### 不用的 Agent 完全无感

```
xiao_mei: 我的工作不需要装环境，从头到尾没碰过容器工具，
          行为和以前一模一样。
```

## 6. 依赖安装的落点

容器隔离的是**运行环境**，不是挂载目录里的文件：

- `create_container` 创建的容器里，`npm install` 默认写项目内的 `node_modules`，`.venv`、构建产物同理。`/workspace/self` 是个人工作目录的映射，所以这些文件会真实落到宿主的 `<team workdir>/agent/<agent名>/` 下，宿主可见，删容器不丢。
- `npm install -g`、系统级 `pip install`、`apt install`、容器内临时目录里的内容只存在于容器内，删容器即消失，宿主全局环境不受影响。
- 共享目录默认只读，`npm install` 到共享目录会被拒绝。
- 没有个人目录映射的容器（已存在的容器、Agent 自己起的容器）里，所有写入都不会回到宿主，需要留存必须回宿主搬运出来。
- 个人工作目录之外的真实仓库路径没有映射进容器，容器内不可见、无法写入；要操作这类路径只能先回宿主。宿主模式下工具没有路径 jail，写这类路径会直接落在宿主机上，不在个人目录里，这部分不受容器保护。

## 7. 产品边界

### 本次交付范围（In Scope）

- 容器管理与容器访问两块能力拆分；
- 5 个工具：`create_container` / `delete_container` / `list_containers` / `enter_container` / `exit_to_host`；
- `enter_container` 只接受已存在的容器（不接受镜像；要别的镜像请先自行起一个容器）；
- `create_container` 创建的容器：个人目录双向映射 + 共享目录只读映射；
- 容器名 `agent-<agent名>-<序号>`；`create_container` 不开放 `image` 参数，使用代码内置的默认镜像 `ubuntu:24.04`；
- 已存在的容器可访问（不校验属主、不做自动挂载、不改变其运行状态）；
- 按「退出后状态 = 进入前状态」的进入规则；
- 五类环境异常提示与 Docker 不可用时的优雅降级；
- Web 侧显示当前执行环境与「自己创建的容器」列表。

### 本次非目标（Out of Scope）

- 系统自动切换执行环境（Agent 不调用就不进容器）；
- Agent 启动时按配置自动切到容器；
- 容器属主校验与准入白名单（后续增强）；
- 跨 Agent 的容器编排；
- 容器内 GUI；
- 容器内跑后端服务或模型；
- 镜像分发给终端用户；
- 容器网络细粒度策略（只做有网 / 无网两档）；
- 一次性任务容器。

### 已知风险（本版接受，不做门禁）

进入一个已存在的容器，等于继承它的全部可见面——它的环境变量、它挂载的所有宿主路径。若该容器挂载了宿主 Docker 控制通道或宿主根目录，Agent 进入后能看到对应内容。本版按「先实现功能」取舍，不做检测与拦截；后续版本可加「挂载探测 + 拒绝列表」。

## 8. 验收标准

- [ ] `create_container` 只创建容器并自动挂载个人目录与共享目录、返回 `container_id` 与容器名，不切换执行环境。
- [ ] 容器名符合 `agent-<agent名>-<序号>` 规则，在宿主机容器列表里能一眼认出属于哪个 Agent。
- [ ] `create_container` 不接受 `image` 参数，一律使用系统内置默认镜像 `ubuntu:24.04`；创建出的容器内 `cat /etc/os-release` 可确认发行版为 Ubuntu 24.04。
- [ ] 自己创建的容器：进入后在容器内写的文件，宿主个人目录可见且内容一致；退出后容器停回停止状态。
- [ ] 自己创建的容器：再次进入仍是同一个 `container_id`，容器里之前装好的依赖仍在。
- [ ] 自己创建的容器：容器处于运行中时再次进入，能正常接管并执行工具。
- [ ] 自己创建的容器：后端崩溃 / 重启后，不残留运行中的容器。
- [ ] `enter_container` 传入镜像名（而非容器）时被明确拒绝，并提示「请先在宿主机上起一个容器」。
- [ ] Agent 在宿主上用 `execute_bash` 执行 `docker run` 起的容器，可通过 `enter_container` 正常进入并执行工具；进入时收到「未挂载个人目录」的提示。
- [ ] 进入一个**运行中**的已存在容器（非本系统创建），退出后该容器仍处于运行状态，内部状态未被打断。
- [ ] 进入一个**已停止**的已存在容器，退出后该容器回到停止状态。
- [ ] 进入未挂载个人目录的已存在容器时，收到「未挂载个人目录、需自行搬运文件」的提示。
- [ ] Agent 自行 `docker run` 起的容器不计入 3 个配额，且 `list_containers` 不返回它。
- [ ] `list_containers` 只返回当前 Agent 自己创建的容器，不含宿主机上其他容器；但仍可通过 `enter_container` 指名进入其他容器。
- [ ] 同一 Agent 最多存在 3 个自己创建的容器（含已停止的）；已满时 `create_container` 被拒绝并提示先删除。
- [ ] 同一时刻只有一个容器处于进入状态；从一个容器直接进另一个容器时，前一个按规则正确处理。
- [ ] 切到容器后，文件读写、命令执行、进程管理工具全部在容器内执行；发言、任务、团队管理工具仍在宿主，权限与门禁不变。
- [ ] 容器内 `pip install` / `npm install` 之后，宿主对应全局环境无变化。
- [ ] 可随时退出回宿主，退出后工具行为与从未使用容器时完全一致。
- [ ] 宿主 → 容器 → 宿主 → 容器来回切换 ≥3 次，无状态错乱、无残留进程、任务与房间上下文不变。
- [ ] 外部删除容器后，Agent 下一次工具调用收到「容器已不存在、文件仍在宿主」的明确提示，而非超时。
- [ ] Docker 未运行、镜像缺失、容器不存在、进入超时、容器不可执行五种情况各有独立可读提示。
- [ ] `delete_container` 只能删除自己创建的容器。
- [ ] 删除当前正在使用的容器时被拒绝，提示先 `exit_to_host` 退出；退出后可正常删除。
- [ ] 删除容器后，宿主个人目录文件完整保留、属主与权限不变。
- [ ] Docker 不可用时，Agent 全部现有能力不受影响。
- [ ] 后端重启后，Agent 的执行环境能正确恢复；恢复失败则回落宿主并告警，不留下悬空状态。
- [ ] 未使用容器的 Agent 行为零变化，全量测试基线不下降。
