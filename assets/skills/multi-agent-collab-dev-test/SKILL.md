# 多 Agent 并行协作规范：开发、测试与交付

## 背景与核心原则

当多个 Agent（或开发者）在同一台机器、同一个代码仓库上并行工作时，它们共享文件系统、Git 对象库、宿主机端口、进程空间与本地数据库。协作出错的主要原因不是代码写错，而是**环境互相污染或测试假阳性，最终得出错误的“验证通过”结论**。

四个环节必须同时闭环，缺一不可：
1. **工作区隔离（Worktree）**：防止别人切分支改乱你的代码，或清理环境时误删他人未提交工作。
2. **运行时隔离（容器 / 端口 / 锁）**：防止端口争抢、共用虚拟环境依赖漂移、或并发读写同一数据库。
3. **测试基准与判据验证**：防止把既有失败算到自己头上，或写出“永远为绿但零保护力”的假阳性测试。
4. **交付与归属可回溯**：结论绑定具体 SHA 与环境参数，不凭 `author` 等无效字段盲猜归属。

# 第一步：开工准备（确认基线与工作区隔离）

## 1.1 先确认基线需求，再确定基点 `$BASE`

开工前先明确任务属于哪类基线需求，再决定是否需要现场取最新 commit：
- **基于特定分支开发**（如“在 `main` / `0.5_dev` 上开发”）：并行开发中分支随时在前进，任务单或旧对话里附带的 SHA 可能已过期。**必须现场执行** `BASE=$(git -C "$REPO" rev-parse <目标分支>)` 获取最新 SHA（必要时先 `fetch`）；若发现任务单附带的参考 SHA 已落后，顺手同步告知。
- **基于指定 Commit 开发 / 复现 / 验收**（如“复现 `<sha>`”、“验收 `<sha>`”）：需求本身锁定了特定历史节点，**直接使用指定 SHA**，严禁擅自拉取分支最新 commit。
- **基于当前工作区 `HEAD` 继续开发**：现场执行 `BASE=$(git -C "$REPO" rev-parse HEAD)` 确认当前 `HEAD` 符合预期后作为基点。

## 1.2 创建独立 Worktree

1. **一任务一 `worktree`，建在主仓库目录之外**：放在主仓库内会被当成未跟踪目录，极易被他人 `git add .` 误提交。
2. **显式指定 `$BASE` 并做方向断言**：不要依赖“当前主工作区在哪个分支”。建好后用 `merge-base --is-ancestor` 验证演进方向（单纯比对两个 SHA 相等/不等没有方向，分不出“基于正确基线新增提交”与“从错误旧基线拉分支”）：
   ```bash
   git -C "$REPO" worktree add -b "$BRANCH" "$WT" "$BASE"   # 验收他人代码用 --detach <sha>
   git -C "$WT" merge-base --is-ancestor "$BASE" HEAD && echo "基线方向正确"
   ```
3. **记录工作区路径与起始 SHA**：建完立刻记下 `$WT` 绝对路径与 `$BASE` SHA，写入最终交付说明。

## 1.3 共享边界与脏工作区安全底线

- **不要用 `git stash`**：`worktree` 仅隔离工作区目录和暂存区，而分支指针、远端、tag 及 **`git stash` 是全仓库共享的**（你的 stash 别人看得到也能误 `pop`）。临时保存请用分支上的临时 commit。
- **主工作区只读不改，严禁动别人的 `worktree`**：不在主工作区切分支或做实验；需要干净基线跑测试或比对时，自己新建 `worktree`。
- **遇到工作区有他人未提交改动时的三条铁律**：
  1. **先存快照**：动手前保存一份 `git status --porcelain`，收尾时对比自证未碰他人文件。
  2. **严禁全目录级清理命令**：一律禁用 `git checkout -- .`、`git restore`、`git stash`、`git clean`。它们不区分修改人，会不可恢复地抹掉其他 Agent 几小时的未提交工作。
  3. **严禁全量暂存**：提交时只按路径 `git add <自己的文件>`，禁用 `git add -A` / `git add .`。

# 第二步：环境准备（并发检查与运行时隔离）

## 2.1 开跑前检查“此刻有没有别人在跑”

凡测试会触碰跨 Agent 共享的独占资源（固定端口、共享数据库、固定写路径）或需复现 CI 环境，均须隔离。在运行测试前，必须通过**双条件**确认无并发冲突：
1. **共享锁包裹**（若项目提供锁脚本）：用 `<lock-script> --bash '<测试命令>'` 执行。锁是唯一能表达“我要独占资源”的机制。
2. **具体进程模式探测**：执行 `pgrep -f "<具体测试命令模式>"`。

> **为什么缺一不可**：只看端口会漏掉不启服务但抢 CPU/临时目录的测试，以及刚启动尚未监听端口的窗口期；只搜宽泛的 `pytest` 会误判宿主机其他无关项目；进程探测能补盲防范绕过锁裸跑的进程。

## 2.2 端口隔离与容器 `note` 复用规范

端口冲突优先让测试框架使用动态随机端口（`port=0`），次选按 Agent 划分固定端口段，或放入独立容器运行。使用容器时遵守以下规范：
1. **先读 `note` 优先复用，新建必写 `note`**：
   - **建前先查**：查看现有容器列表及 `note`（备注说明）。若有用途匹配、依赖就绪且空闲的容器，**直接复用**，避免重复建容器和重复装包。
   - **建后必注**：新建或配好容器后，必须写入清晰的 `note`（标明容器用途、项目/语言版本、挂载约定），方便后续任务或其他 Agent 识别复用。
2. **只挂自己的独立 `worktree`**：目录挂载会把构建产物、`__pycache__`、测试库写回宿主机，绝不能挂载主仓库或他人 `worktree`（只验不改也可用文件复制）。
3. **记录容器内环境版本**：进容器先记录语言、测试框架、内核版本及 CPU 核数（写入交付报告）；**禁止**在容器内调用宿主机虚拟环境的绝对路径。

## 2.3 真实数据的只读硬约束

测试或排查涉及落盘与数据库时，先确认目标路径是临时目录还是真实数据。**严禁在真实业务数据上运行任何会产生写入的测试**，也不要靠“开事务测完回滚”规避（事务会抢写锁阻塞活库，且中断即污染）。排查真实库必须用只读模式（如 `sqlite3 "file:/path/to/data.db?mode=ro"`）。

# 第三步：执行测试（基准比对与判据验证）

## 3.1 执行顺序与容器并发控制

1. **固定三步顺序**：先在未改动的 `$BASE` 上跑基线记录结果 → 再用相同环境与命令跑改动后代码 → 比对前后差量。跳过基线会把仓库既有失败误判给自己，或把自己引入的失败当成既有问题放过。
2. **禁用容器内 `-n auto`**：容器常受 CPU 限额限制，`pytest -n auto` 会按宿主机物理核数开进程导致超时或 OOM（易被误判为并发 bug）。应先串行（`-p no:cacheprovider`）跑稳，再显式指定小并发数（如 `-n 4`）。

## 3.2 验证判据本身的有效性（三步变异验证）

“改动后测试变绿”不能证明测试本身有效——断言可能恒真、过宽或漏掉了目标分支。对关键修复或新增判据，必须执行**三步变异验证**：
1. **记录基线状态**（红或绿）。
2. **注入变异（故意改坏被保护的核心实现）**：**实跑命令**，判据必须报错（变红）。
3. **恢复代码**：**实跑命令**，判据必须恢复通过（变绿）。

**执行约束**：
- **必须实跑，禁止读代码脑补**：脑补只是假设，实跑输出才是证据。
- **一次只改坏一处**：避免整段重写导致变红后分不清是哪条断言生效。
- **防范恒真判据**：两侧必然相等的比对（如对同一对象算两次哈希、恒等变换）永远为绿且零保护力，只能作防伪附注，不能当主判据；同样不要用活库的行数或时间戳绝对值当判据（应改用 ID 差集或内容哈希等稳定量）。

# 第四步：提交与合并

1. **分支规范**：一任务一独立分支，严禁往主干（`main` / `master` / `dev`）直接提交半成品。分支命名采用 `<type>/<short-desc>`（如 `feat/agent-memory`、`fix/ws-auth-no-ack`），全小写连字符分词，**不带人名、不带日期**。
2. **按路径提交**：提交前检查 `git status --short`、`diff --stat "$BASE"...`、`log --oneline "$BASE"..`；只按具体文件路径 `git add <file>`，一提交做一件事；未经明确指令不自动提交。
3. **合并与冲突**：合并前重新 `rev-parse` 确认目标分支当前最新位置；无冲突合并后可比对 `<feature-sha>^{tree}` 与 `HEAD^{tree}` 确认内容一致；遇到冲突**严禁用 `git checkout --theirs .` 或 `--ours .` 整片丢弃他人代码**，必须逐处处理或询问确认。

# 第五步：交付验收、归属判断与收尾清理

## 5.1 交付报告标准模板

所有结论必须绑定具体 SHA 与环境参数，禁止笼统写“全部通过”或把宿主机与容器数据混排对比：

```text
结论：<一句话明确结论，可判定真假>
基线与工作区：worktree <绝对路径> ｜ 基点 <BASE_SHA> → 当前 <HEAD_SHA>（分支 <branch>）
运行环境：<本机 或 容器ID(含note)> ｜ python/node <ver> ｜ pytest <ver>
执行命令：<可直接复制重跑的完整命令原文>
关键输出：<原文关键行，必须含 passed / failed / skipped 具体计数>
未覆盖项：<未跑的测试、无法执行的验证及原因>
```

## 5.2 交接验收与“提交归属”判断规则

- **交给他人验收**：提供**分支名 + 具体 SHA**；验收方用 `git worktree add --detach "$WT" <sha>` 在独立目录验证，结论绑定 `<sha>`。
- **如何判断“某个提交或改动是谁做的”**：
  - **唯一可靠依据**：对方明确汇报的 `SHA` + `git reflog` + 会话/工具调用记录。
  - **四个“零信息”字段（正反方向均不成立）**：
    1. `author` / `committer`（多 Agent 常共用同一机器全局 Git 配置或账号，或同一人多种拼写）
    2. `worktree` 目录名（仅代表建目录时的命名，目录可能被借用或切换分支）
    3. 分支名前缀（可能是历史遗留或问题提出人，非实际修改人）
    4. 提交时间戳（并行开发时同一分钟内常有多个不同来源的提交）
  - **实践准则**：需要归属时直接询问或查会话记录，不从上述字段猜谜；汇报只写“提交 `<sha>`”不写“XX 的提交”；不用 Git `author` 统计工作量或追责；仅凭 `author` 被问及归属时，直接回答“仅凭 Git 记录无法确定，需查会话记录或对应 SHA”。

## 5.3 收尾清理

- **清理 `worktree` 并立即 `prune`**：执行 `git worktree remove "$WT"` 后顺手跑一次 `git worktree prune`，避免失效记录堆积导致 `worktree list` 混杂难读（多时可用 `--porcelain` 过滤）。尚未合并的实验分支不要删，保留 SHA 供回溯。
- **容器按 `note` 决定去留**：一次性临时容器用完销毁；写明 `note` 供复用的容器保留环境本身（仅清理残留测试进程与临时文件），切勿误删公共或他人注明复用的容器。
