# 多 Agent 协作：开发 / 测试 / 提交

多个 Agent 同时改一个仓库时，出错最多的地方不是写错代码，而是**互相污染之后还得出"通过"这个结论**。

三类污染对应三个部分：

| 污染 | 表现 | 对应手段 |
|---|---|---|
| 文件冲突 | 别人切分支你代码变了；未提交改动串台 | 开发：`git worktree` 隔离 |
| 运行时冲突 | 端口被占、共用依赖版本漂移、测试库互相写 | 测试：独立/容器环境隔离 |
| 主干污染 | 半成品混进主干；不知道某行改动是谁的 | 提交：独立分支 + 命名规范 |

三部分必须**一起**做。只做一层的常见后果：

- **只 worktree、不隔离测试环境**：所有人共用一个虚拟环境/一个后端端口。A 升级了一个包、占着 8180，B 跑出来的失败其实是 A 造成的，两边的数字互相不可比。
- **只隔离测试环境、不 worktree**：容器挂的是同一个宿主目录。别人 `git checkout` 换分支时，你容器里的代码跟着变，你的测试结果与你以为的 SHA 不对应。
- **都不做、只靠"我会小心"**：这不是隔离，是运气。而运气不可复现。

# 一、开发：用 worktree 避免文件冲突

`git worktree` 让同一仓库的多个分支同时检出到不同目录，共享同一个 `.git`，不复制历史、不占双倍空间。

## 规则

1. **一个任务一个 worktree**，目录名带任务标识，方便事后回看。
2. **放在自己的目录下**，绝对不要放进主仓库目录内——否则会以未跟踪文件的形式出现在主仓库的 `git status` 里，容易被别人顺手 `git add .` 提进去。
3. **显式指定基点**（分支名或 SHA）。不要依赖"当前在哪个分支"，那是猜；猜错的代价是你在错误的基础上做了一整天改动。
4. **主工作区只用于"看"，不用于"实验"**。不要在别人正在用的 checkout 上切分支，那会直接打断对方。
5. **验收别人的分支时用 detached 检出**，避免手滑把改动提交到对方分支上。

## 建 worktree

```bash
WT_ROOT="${WT_ROOT:-$HOME/worktrees}"   # 你自己的根目录，按习惯改
REPO="${REPO:-.}"                        # 主仓库路径
BRANCH="feat/my-change"
BASE="origin/main"                       # 基点：远端分支或具体 SHA
WT="$WT_ROOT/$(date +%m%d)_$BRANCH"

git -C "$REPO" fetch origin
git -C "$REPO" worktree add -b "$BRANCH" "$WT" "$BASE"
git -C "$WT" rev-parse --short HEAD      # ← 立刻记下这个 SHA
```

验收别人（只验不改）：

```bash
git -C "$REPO" worktree add --detach "$WT" <sha-or-branch>
```

建完立刻记两件事，报数要用：**worktree 路径** 和 **基点 SHA**。分支名会移动，SHA 不会。

## 清理

```bash
git -C "$REPO" worktree remove "$WT"     # 有未提交改动时加 --force
git -C "$REPO" worktree list             # 标 prunable 的可 git worktree prune
```

## 唯一的例外：这里反而要共享

worktree 隔离的是**工作区**，不是 `git` 本身。所以：

- **共享的**：分支指针、`origin` 远端、tag、`git log`。你在自己 worktree 里推上去的分支，别人 `fetch` 就能看到。
- **不共享的**：工作区文件、`git status`、`git stash`（stash 是仓库级的，别人会看到你的 stash——**不要用 stash 做临时保存**，用 commit）。

**不要在别人的 worktree 里执行任何写操作**（包括 `git checkout`、`git reset`、`git stash pop`）。要动就自己建一个。

# 二、测试：各自独立跑，需要时进容器

## 2.1 先判断要不要容器

不是所有测试都需要容器。用冲突面判断：

| 测试类型 | 要不要容器 | 理由 |
|---|---|---|
| 纯函数 / 纯逻辑单测 | 不需要 | 不碰端口、不碰磁盘、不碰共享状态 |
| 会连数据库的集成测试 | **看情况** | 若测试能自动隔离到临时库，不需要；若会打到共享库，必须隔离 |
| 会启动服务的测试（后端、mock 服务） | **需要** | 端口是机器级独占资源，两个 Agent 同时跑必撞 |
| 会写文件的测试 | **看情况** | 写到临时目录就行；写到共享目录必须隔离 |
| CI 上跑、想复现 CI 结果 | **需要** | 版本、系统工具链必须与 CI 一致，否则失败不可归因 |

判据一句话：**这个测试会不会碰到"另一个 Agent 也能碰到的独占资源"？** 会，就隔离。

## 2.2 进容器后先记录量具，不是先装依赖

```bash
python3 --version; pip --version
node --version 2>/dev/null; npm --version 2>/dev/null
pytest --version 2>/dev/null
uname -a; nproc
```

这些数字要进交付说明。缺了它们，所有结论只能当"我觉得"。

## 2.3 代码怎么进容器

- **挂载**：改代码即时生效，但容器内的构建产物、`__pycache__`、测试数据库也会写回宿主目录。要挂就挂**你自己的 worktree**，绝不挂别人的、绝不挂主仓库。
- **复制**：干净，但改一次同步一次。适合"只验不改"的验收场景。

**不要**在容器里引用宿主虚拟环境的绝对路径。容器里没有那个目录，或者有但版本不同。

装依赖受网络限制时用就近镜像（示例，按实际网络替换）：

```bash
pip install -r requirements.txt -i https://pypi.example.com/simple --trusted-host pypi.example.com
```

## 2.4 端口类冲突的三种解法

按侵入性从低到高：

1. **让测试自己随机端口**（最好）。多数框架支持 `port=0` 由系统分配。
2. **按 Agent 分配固定端口段**。约定每人一段，避免临时协商。
3. **进容器**。容器的网络命名空间天然隔离，两个容器都可以用同一个端口。

## 2.5 跑测试的顺序 —— 顺序本身就是方法

1. **先跑基线**：在未改动的基点上跑同一批用例（或同一个失败用例），记下颜色。
2. **再跑你的改动**：同样的命令、同样的环境。
3. **最后比对**：只有"基线绿 → 改动后红/绿"的差异才属于你。

跳过第 1 步的代价是双向的：你会把仓库里早就存在的失败当成自己引入的，也会把自己引入的失败当成"本来就红"。**不知道基线什么颜色，就无法判断你看到的是什么。**

并行度：容器的 CPU 常被限额。`-n auto` 会按宿主机核数开进程，导致随机超时或 OOM，看起来像"代码有并发 bug"。

```bash
pytest -q -p no:cacheprovider     # 先串行拿干净结果
pytest -q -n 4                    # 确认稳定后再考虑并行
```

## 2.6 碰真实数据时的硬约束

测试若会落盘、写数据库，先确认三件事，缺一就别跑：

1. 它写的是**临时路径**还是你挂进来的**真实数据**？
2. 真实数据的路径是什么，有没有备份？
3. 只读能否满足本次验证？

只读连接的正确姿势（SQLite 示例，其他数据库同理）：

```bash
sqlite3 "file:/path/to/data.db?mode=ro" "SELECT COUNT(*) FROM t;"
```

**绝不在有真实数据的地方跑会写入的测试**。也不要用"开个事务、测完回滚"给自己壮胆——事务会拿写锁，活库上有其他进程时直接失败，而且回滚靠的是你自己不犯错。

# 三、提交：独立分支 + 命名规范

## 3.1 一条铁律

**一个任务一个分支，不往主干直接提交。**

主干（`main` / `master` / `dev` 这类长期分支）上的每一个提交都应该是"能被人拉下来直接用的"。半成品、临时调试、跑一半的改动一律留在自己的分支上。

## 3.2 分支命名规范

采用 `<类型>/<简短描述>` 形式，全小写，用连字符分词，不用中文、空格、下划线。

| 类型 | 用于 | 例子 |
|---|---|---|
| `feat/` | 新功能 | `feat/agent-memory` |
| `fix/` | 修 bug | `fix/room-runtime-state-ready` |
| `refactor/` | 重构，不改外部行为 | `refactor/job-naming` |
| `test/` | 只加/改测试 | `test/memory-flow-coverage` |
| `docs/` | 只改文档 | `docs/skill-collab-guide` |
| `chore/` | 构建、依赖、配置 | `chore/bump-version` |

描述部分要点：

- **说做了什么，不说"改了一下"**。`fix/ws-auth-no-ack` 好过 `fix/bug1`。
- **长度控制在三四个词**。太长了在命令行里输入困难。
- **不要带人名**。`alice/fix-xxx` 这种形式在多人协作里没意义，而且会让人以为只能由某个人改。
- **不要带日期**。日期在 commit 里已经有了，放到分支名里只会让名字变长。

## 3.3 提交前自检

```bash
git -C "$WT" status --short          # 有没有混进不该提交的文件
git -C "$WT" diff --stat "$BASE"...  # 改动范围是否与任务一致
git -C "$WT" log --oneline "$BASE".. # 提交列表是否干净
```

重点看 `status` 里有没有：构建产物、`__pycache__`、临时脚本、别人的文件、编辑器配置。

## 3.4 提交信息

- **一条提交做一件事**。混在一起会让 review 和回滚都变难。
- **标题一句话说清"改了什么"**，正文说"为什么"。
- **不要自动提交**。等明确指令再提交——这是团队的既有约定，多数项目都这么要求。

## 3.5 交给别人验收

- 告诉对方**分支名 + 具体 SHA**。只给分支名不够，分支会前进。
- 对方应当用 **detached 检出**到自己独立的 worktree 里验，不要直接在你的分支上验。
- 结论与 SHA 绑定：写"在 `<sha>` 上验证通过"，不要写"这个分支验证通过"。

## 3.6 合并

- 合并前确认目标分支的**当前**位置，不要用几小时前记下的 SHA。
- 合并后**对比树内容**确认没有额外变化：

```bash
git rev-parse <feature-sha>^{tree}
git rev-parse HEAD^{tree}        # 若两者相同，说明内容零变化
```

- 有冲突时**不要**用 `git checkout --theirs .` / `--ours .` 整片认领。这会把对方的改动整体丢弃，且不会有人发现。冲突必须逐个处理或问清楚。

# 四、报数：让结论可回溯

每条结论都要能指认到外部依据。统一模板：

```text
结论：<一句话，可判定真假>
量具：worktree <路径> @ <SHA> ｜ 环境 <容器ID或本机> ｜ python <ver> ｜ pytest <ver>
命令：<原文，可直接复制重跑>
输出：<原文关键行，含 passed/failed/skipped 计数>
```

禁止的写法：

- "全部通过" —— 要给 `passed/failed/skipped` 三个数
- "应该没问题" —— 这是假设，标注出来，别当结论
- 把宿主和容器的数字并排写 —— 两套环境，数字不可比
- 只写分支名不写 SHA —— 分支会前进，结论就复现不了
- 用行数、时间戳的绝对值当判据 —— 活数据会漂，判据当场失效。用 id 差集、内容哈希这类稳定量

# 五、反模式对照

| 反模式 | 后果 |
|---|---|
| 在主工作区 checkout 别人的分支做实验 | 打断别人；对方跑出的结果对不上自己的代码 |
| worktree 建在主仓库目录内 | 被 `git status` 视为未跟踪，容易误提交 |
| 用 `git stash` 做临时保存 | stash 是仓库级的，别人能看到甚至 pop 掉 |
| 只记分支名不记 SHA | 分支前进后结论无法复现，验收无法回溯 |
| 两个 Agent 同时起服务抢同一个端口 | 随机失败，且双方都以为是对方代码的问题 |
| 只 worktree 不隔离环境 | 依赖版本漂移，数字互相不可比 |
| 只隔离环境不 worktree | 容器里代码跟着别人切分支变 |
| 容器里引用宿主虚拟环境绝对路径 | 路径不存在或版本不同，报错与被测代码无关 |
| 直接用真实数据库验证 | 不可逆；活库持续变化，行数类判据失效 |
| 用行数/时间戳绝对值做判据 | 活库会漂。用 id 差集、内容哈希这类稳定量 |
| 依赖 `-n auto` | CPU 受限 → 随机超时 → 误判为并发 bug |
| 只在改完后跑一次，不跑基线 | 既有失败算到自己头上，或自己的失败当成既有 |
| 半成品直接提交主干 | 主干不可用，所有人都被阻塞 |
| 用 `--theirs` / `--ours` 整片认领冲突 | 对方改动被静默丢弃，无人发现 |

# 六、收尾

交付说明里必须包含：

1. **分支名 + SHA**
2. **worktree 路径**
3. **测试环境标识 + 语言/框架版本**
4. 每条验证的**命令原文**和**数字**
5. 未跑的东西、跑不了的、以及为什么

清理容器和 worktree 是安全的：**结论绑定 SHA 和量具，不绑定目录**。但未合并的实验分支不要删，保留 SHA 供验收回溯。
