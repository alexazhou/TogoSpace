# 多 Agent 并行协作规范：开发、测试与交付

## 背景与适用场景

当多个 Agent（或开发者）在**同一台宿主机、同一个本地代码仓库**上并行领任务时，它们默认共享同一套文件系统、Git 仓库、宿主机端口、进程空间与本地数据库。

如果不做隔离与规范约束，最容易发生的问题不是“代码写错”，而是**环境互相污染或测试假阳性，最终得出错误的“验证通过”结论**：

| 典型风险 | 具体表现 | 解决手段 | 对应章节 |
|---|---|---|---|
| **工作区冲突** | 别人切分支导致你的代码跟着变；清理环境时误删他人未提交工作 | 使用 `git worktree` 隔离工作目录；严禁全目录清理命令 | 第一步 |
| **运行时干扰** | 多个测试争抢同一端口、共用依赖版本漂移、并发读写同一数据库 | 开工前探测锁与进程；按需使用容器/独立端口隔离 | 第二步 |
| **测试假阳性** | 不跑基线就下结论；断言本身恒真或漏掉目标路径，以为“绿了就是对的” | 先跑基线再跑改动；对新增判据做“改坏实现必变红”的变异验证 | 第三步 |
| **主干污染与归属混乱** | 半成品直接提交主干；混入他人未提交文件；凭 `author` 盲猜提交归属 | 独立分支按路径提交；交付绑定具体 SHA；归属只认 SHA 与会话记录 | 第四、五步 |

**以上环节必须配合执行：**
- **只用 `worktree`、不隔离测试环境**：所有 Agent 共用一个虚拟环境或服务端口。A 升级了依赖包或占着 8180 端口，B 跑出的失败其实是 A 造成的，两边的结果无法对比。
- **只隔离测试环境、不用 `worktree`**：容器挂载的是同一个宿主机目录。其他 Agent 执行 `git checkout` 切分支时，你容器里的代码随之改变，测出来的结论与你以为的 SHA 根本对应不上。
- **只看测试通过、不验证判据有效性**：测试本身可能恒真，或者根本没覆盖你要保护的代码路径，表面全绿但零保护力。

# 第一步：开工准备（确认基线与工作区隔离）

## 1.1 先确认基线需求，再决定基点 SHA

开工第一件事是**明确本次任务的基线需求属于哪一种**，再按对应方式确定基点 `$BASE`：

| 需求场景 | 是否需要现场取最新 commit | 如何确定 `$BASE` |
|---|---|---|
| **1. 在特定分支上开发**（如“基于 `main` / `0.5_dev` 开发”） | **需要**。并行开发中分支随时在前进，任务单或几小时前对话里顺带提到的 SHA 可能已过期 | 现场执行 `BASE=$(git -C "$REPO" rev-parse <目标分支>)` 获取该分支当前最新 SHA（必要时先 `git fetch`） |
| **2. 在指定 Commit 上开发 / 复现 / 验收**（如“复现 `<sha>` 的问题”、“验收 `<sha>`”） | **不需要（严禁擅自取最新）**。需求本身就锁定在特定历史节点上 | 直接使用需求指定的固定 SHA：`BASE=<指定SHA>` |
| **3. 在当前工作区 `HEAD` 上继续开发** | **需现场解析当前 `HEAD`**，但不要切去远端或主干最新位置 | 现场执行 `BASE=$(git -C "$REPO" rev-parse HEAD)`，确认当前 `HEAD` 符合预期后作为基点 |

确定 `$BASE` 并建好工作区后，执行方向断言：

```bash
git -C "$WT" merge-base --is-ancestor "$BASE" HEAD && echo "基线方向正确"
```

配套纪律：
- **把实际使用的 `BASE` 写进交付说明**：让验收人能基于你实际使用的基点复现，而不是拿他猜测的 SHA 比对。
- **必须用 `merge-base --is-ancestor` 做方向断言**：单纯比较两个 SHA 相等或不等是没有方向的，分不出“我在正确基线上新增了提交”和“我从错误的旧基线拉了分支”；`--is-ancestor` 能明确验证 `HEAD` 是否基于 `$BASE` 演进。
- **发现分支基线过期时主动同步**：当需求是“基于某分支最新位置开发”，但任务单上附带的参考 SHA 已经落后于该分支最新提交时，顺手告知相关方一声，不要盲目照抄过期 SHA。

## 1.2 创建独立 Worktree

`git worktree` 允许同一仓库的多个分支同时检出到不同目录，共享同一个 `.git` 对象库，不占双倍体积，且各目录的文件修改完全独立。

### 核心规则
1. **一个任务一个 `worktree`**：目录名带上任务或分支标识，方便区分。
2. **必须建在主仓库目录之外**：绝不要建在主仓库目录内部——否则会被主仓库的 `git status` 当成未跟踪目录，极易被其他 Agent 顺手 `git add .` 提交进去。
3. **显式指定基点（`$BASE`）**：不要依赖“当前主工作区在哪个分支”，那很容易猜错。
4. **主工作区只读不改**：主工作区只用于查看，不要在主工作区直接切分支或做实验，否则会直接打断正在参考主工作区的其他 Agent。
5. **验收他人代码用 `--detach`**：只验不改时使用分离头指针检出，防止手滑把调试代码提交到对方分支上。

### 标准命令

开发新任务：

```bash
WT_ROOT="${WT_ROOT:-$HOME/worktrees}"   # 独立的 worktree 根目录，放在主仓库外
REPO="${REPO:-.}"                        # 主仓库路径
BRANCH="feat/my-change"
WT="$WT_ROOT/$(date +%m%d)_${BRANCH//\//_}"

# 按 1.1 节确认的需求设置 BASE（三选一）：
# 1) 基于远端/本地分支最新：git -C "$REPO" fetch origin && BASE=$(git -C "$REPO" rev-parse origin/main)
# 2) 基于指定固定 commit：  BASE="<指定SHA>"
# 3) 基于当前工作区 HEAD：  BASE=$(git -C "$REPO" rev-parse HEAD)

git -C "$REPO" worktree add -b "$BRANCH" "$WT" "$BASE"
git -C "$WT" rev-parse --short HEAD      # 立刻记下起始 SHA
```

验收他人提交（只验不改）：

```bash
git -C "$REPO" worktree add --detach "$WT" <sha-or-branch>
```

建完后立刻记录两项信息（交付报告必填）：**`worktree` 绝对路径** 和 **起始基点 SHA**。

## 1.3 Worktree 的共享边界与脏工作区底线

`worktree` 隔离的是**工作区目录和暂存区**，但底层 Git 仓库仍是同一个：
- **隔离的（各自独立）**：工作区文件、`git status`、暂存区（index）、当前 `HEAD`。
- **共享的（全局可见）**：分支指针、`origin` 远端、tag、`git log`、以及 **`git stash`**。
  > **注意**：`git stash` 是全仓库共享的，你 stash 的内容别人能看到甚至误 `stash pop` 掉。**严禁用 `git stash` 做临时保存**，请改用分支上的临时 commit。

### 当工作区里存在他人的未提交改动时

**严禁在其他 Agent 的 `worktree` 里执行任何写操作**（包括 `checkout`、`reset`、`stash pop`）。如果你不得不在主工作区或共享目录操作，且发现已经有不属于你的未提交文件，必须遵守三条底线：

1. **动手前先存状态快照**：先跑一次 `git status --porcelain` 保存下来。收尾时对比快照，既能确认自己没误碰他人文件，也能在出现争议时自证。
2. **严禁全目录级清理命令**：一律禁用 `git checkout -- .`、`git restore`、`git stash`、`git clean`。它们是**全目录级**操作，不会区分“只清理我的修改”，一旦执行就会把其他 Agent 几小时的未提交工作彻底抹掉且**不可恢复**。
3. **需要干净环境时，新建 `worktree`**：如果要跑全量测试或做干净的差异比对，自己新建一个独立 `worktree`，绝不要靠“把主工作区清理干净”来凑合。

# 第二步：环境准备（并发检查与运行时隔离）

## 2.1 判断是否需要独立环境或容器

并非所有测试都要进容器，按**是否触碰跨 Agent 共享的独占资源**来判断：

| 测试类型 | 是否需要容器/独立环境 | 原因 |
|---|---|---|
| 纯函数 / 纯逻辑单元测试 | 不需要 | 不碰端口、不写共享磁盘、不改全局状态 |
| 连接数据库的集成测试 | **视情况而定** | 若自动创建独立临时库则不需要；若连接固定共享库则必须隔离 |
| 启动服务的测试（后端、Mock 服务） | **需要** | 固定端口是机器级独占资源，两个 Agent 同时跑必然冲突 |
| 读写文件的测试 | **视情况而定** | 写独立临时目录即可；写仓库内固定路径则必须隔离 |
| 复现 CI 结果 | **需要** | 依赖版本、系统工具链需与 CI 完全一致，否则失败无法归因 |

## 2.2 开工前检查“此刻有没有别人在跑”

即使选好了测试方案，跑测试前也必须确认**当前没有其他 Agent 正在占用同一套资源**。检查必须满足**双条件**，缺一不可：

```bash
# 条件 1：使用项目共享锁脚本包裹测试命令（若项目提供）
<lock-script> --bash '<你的测试命令>'

# 条件 2：按具体命令模式探测正在运行的同类测试进程
pgrep -f "<你实际的测试命令模式>" || echo "当前无同类测试进程"
```

为什么单看一项不够：
- **只看端口不够**：不启动网络服务的测试照样会争抢 CPU 和共享临时目录；而且进程刚启动、尚未绑定端口的窗口期内，端口也是空的。
- **只看宽泛进程名不够**：只搜 `pytest` 可能会匹配到宿主机上其他无关项目的进程。因此必须**按具体的测试命令模式匹配**。
- **共享锁与进程探测互补**：锁是唯一能表达“我要独占资源”的机制；而进程探测用于补盲，防范有人绕过锁直接裸跑测试。

## 2.3 解决端口冲突的三种方式

按改动成本从低到高排序：
1. **让测试动态分配随机端口（推荐）**：多数测试框架支持指定 `port=0`，由操作系统分配空闲端口。
2. **按 Agent 划分固定端口段**：事先约定每个 Agent 使用不同的端口区间，避免临时碰撞。
3. **放入独立容器运行**：容器拥有独立的网络命名空间，不同容器内可以使用相同的默认端口。

## 2.4 容器环境使用规范

如果测试需要在容器内执行：

1. **先读 `note` 优先复用已有容器，新建时写好 `note`**：
   - **建前先查**：准备容器前，先查看当前已有的容器列表及其 `note`（备注/说明信息）。如果已有用途匹配、依赖就绪且当前空闲的容器，**直接复用**，避免每次新建容器、重复拉取和安装依赖。
   - **建后必注**：若现有容器不满足需求而新建容器（或对容器环境做了重要配置），必须为容器写入清晰的 `note`，标明**容器用途、对应的项目/语言环境版本、挂载约定**，方便后续任务或其他 Agent 识别复用。
2. **进容器先记录环境版本（再装依赖或跑测试）**：
   ```bash
   python3 --version; pip --version
   node --version 2>/dev/null; npm --version 2>/dev/null
   pytest --version 2>/dev/null
   uname -a; nproc
   ```
   这些环境信息必须写进最终交付说明，没有环境版本支撑的测试数字不具备可比性。
3. **代码进容器的方式**：
   - **目录挂载**：改代码即时生效，但容器内产生的构建产物、`__pycache__`、测试数据库也会写回宿主机。**要挂只能挂你自己的独立 `worktree`**，绝不能挂主仓库或别人的 `worktree`。
   - **文件复制**：环境彻底干净，但每次修改需重新同步，适合“只验不改”的验收场景。
4. **路径与网络注意**：
   - **不要**在容器里直接调用宿主机虚拟环境的绝对路径（如宿主机的 `.venv/bin/pytest`），容器内路径或底层动态库往往不兼容。
   - 容器内安装依赖遇到网络受限时，使用就近镜像源（按实际环境替换）：
     ```bash
     pip install -r requirements.txt -i https://pypi.example.com/simple --trusted-host pypi.example.com
     ```

## 2.5 触碰真实数据时的只读硬约束

如果测试或排查脚本会读写磁盘或数据库，动手前先确认三件事：
1. 它访问的是**独立临时路径**，还是挂载进来的**真实业务数据**？
2. 真实数据的路径在哪，是否有备份？
3. **只读模式**能否满足本次验证需求？

连接真实数据库进行排查时，必须使用只读连接（以 SQLite 为例）：

```bash
sqlite3 "file:/path/to/data.db?mode=ro" "SELECT COUNT(*) FROM t;"
```

**严禁在挂有真实数据的目录上运行会产生写入的测试。** 也不要试图用“开启事务、测完回滚”来规避——事务会持有写锁导致线上或其他进程报错，且一旦脚本异常中断就会造成不可逆污染。

# 第三步：执行测试（基准比对与判据验证）

## 3.1 测试执行顺序与并行度控制

跑测试必须遵循固定的三步顺序：
1. **先跑基线（Baseline）**：在未修改的 `$BASE` 代码上运行同一批测试命令，记录初始结果（通过或失败）。
2. **再跑改动后代码**：在相同环境、用完全相同的命令运行修改后的代码。
3. **比对前后差异**：只有“基线通过 → 改动后失败/通过”或“基线失败 → 改动后修复”的差量，才属于你本次改动的真实影响。

> **为什么不能跳过第 1 步**：如果不跑基线，你既可能把仓库里原本就存在的失败误判成自己引入的 bug，也可能把自己新引入的失败当成“本来就坏的”而放过。

**控制容器内的并行度**：
容器通常会限制 CPU 核数，而 `pytest -n auto` 会读取宿主机的物理总核数启动大量工作进程，导致容器内频繁超时或 OOM，看起来像“代码有偶发并发 bug”。

```bash
pytest -q -p no:cacheprovider     # 第一遍先串行跑，拿干净稳定的结果
pytest -q -n 4                    # 确认稳定后，再指定明确的并发数
```

## 3.2 验证判据本身的有效性（变异验证）

“基线通过 → 改动后通过”只能说明代码没把现有测试跑崩，**不能证明你写的测试或判据真的管用**——判据本身可能是恒真的、断言过宽的，或者根本没走到你要保护的那条代码分支。

对关键修复或新增测试，必须执行**三步变异验证**：

1. **基线状态**：记录改动前的测试状态（红或绿）。
2. **注入变异（改坏实现）**：把被保护的那段核心业务实现**故意改坏**，实跑测试，此时判据**必须报错（变红）**。
3. **恢复验证（改回实现）**：把业务实现恢复正常，实跑测试，此时判据**必须恢复通过（变绿）**。

只看改动后变绿，分不出“判据有效”和“判据恒真”；只看改坏后变红而不看恢复，也无法闭环。执行变异验证时须遵守三条约束：
- **变异必须真跑命令，禁止靠读代码脑补**：“我看过逻辑了，这里改坏肯定会报错”只是主观假设，不是实际运行证据。
- **变异粒度要细**：一次只改坏一处关键逻辑。如果整段重写同时改变了多个行为，就算测试变红，你也无法确认是哪条断言真正起了作用。
- **专门防范“恒真判据”**：如果两侧比对的是必然相等的量（例如对内存中同一个对象算两次哈希、或者做恒等变换比对），它永远为绿且不提供任何保护力。这类检查只能当辅助防伪校验，**绝不能作为主判据**。

# 第四步：提交与合并（分支规范与变更收敛）

## 4.1 分支铁律与命名规范

**铁律：一个任务一个独立分支，严禁直接往主干（`main` / `master` / `dev`）提交代码。** 主干上的每一次提交都应当是可独立运行、经过验证的状态，半成品和调试代码一律留在任务分支上。

分支命名采用 `<类型>/<简短描述>` 格式，全小写字母，单词间用连字符 `-` 分隔，不使用中文、空格或下划线：

| 前缀类型 | 适用场景 | 示例 |
|---|---|---|
| `feat/` | 新增功能 | `feat/agent-memory` |
| `fix/` | 修复缺陷 | `fix/room-runtime-state-ready` |
| `refactor/` | 重构（不改变外部行为） | `refactor/job-naming` |
| `test/` | 新增或修正测试 | `test/memory-flow-coverage` |
| `docs/` | 仅修改文档 | `docs/skill-collab-guide` |
| `chore/` | 构建、依赖、配置杂项 | `chore/bump-version` |

命名注意：
- **描述具体行为，控制在 3~4 个词**：如 `fix/ws-auth-no-ack`，避免 `fix/bug1` 这种无意义命名。
- **不要带人名或 Agent 名**：不要写 `alice/fix-xxx`，分支按任务归属而非按人私有。
- **不要带日期**：提交记录自带时间戳，分支名加日期只会增加命令行输入负担。

## 4.2 提交前自检与按路径暂存

提交前在自己的 `worktree` 中执行三项自检：

```bash
git -C "$WT" status --short          # 检查是否有未跟踪的临时文件、构建产物混入
git -C "$WT" diff --stat "$BASE"...  # 检查修改的文件范围是否与任务目标一致
git -C "$WT" log --oneline "$BASE".. # 检查提交历史是否干净
```

暂存与提交规范：
- **按具体文件路径 `git add <file>`，严禁使用 `git add -A` 或 `git add .`**：全量添加极易把临时调试脚本、`__pycache__`、或者共享工作区里其他 Agent 的未提交改动一并打包进你的 commit，且从 commit message 上完全看不出来。
- **一条提交做一件事**：逻辑独立的改动分开提交，方便后续 code review 与独立回滚。
- **不要自动提交**：遵循项目协作约定，完成开发与验证后等待明确指令再执行 `git commit`。

## 4.3 合并与冲突处理

- **合并前重新确认目标分支最新位置**：执行合并前再次 `rev-parse` 目标分支，不要使用几小时前记下的旧 SHA。
- **合并后校验目录树一致性**：确认无冲突合并没有意外篡改文件内容：
  ```bash
  git rev-parse <feature-sha>^{tree}
  git rev-parse HEAD^{tree}        # 若无额外合并改动，两侧 tree SHA 应完全一致
  ```
- **严禁整片覆盖冲突**：遇到冲突时，**绝不可使用 `git checkout --theirs .` 或 `git checkout --ours .`**。这会将对方或自己的整片修改静默丢弃且不留痕迹。冲突必须逐文件比对合并，或向相关方确认。

# 第五步：交付验收、归属判断与收尾清理

## 5.1 交付报告标准模板

所有测试结论与交付说明必须绑定具体 SHA 与环境信息，确保任何人都能复现。统一使用以下格式汇报：

```text
结论：<一句话明确结论，可判定真假>
基线与工作区：worktree <绝对路径> ｜ 基点 <BASE_SHA> → 当前 <HEAD_SHA>（分支 <branch>）
运行环境：<本机 或 容器ID> ｜ python <ver> ｜ pytest <ver>
执行命令：<可直接复制重跑的完整命令原文>
关键输出：<原文关键行，必须包含明确的 passed / failed / skipped 数量>
未覆盖项：<未跑的测试、无法执行的验证及具体原因>
```

### 交付汇报禁止事项
- **禁止只写“全部通过”** —— 必须给出 `passed / failed / skipped` 具体计数。
- **禁止把“应该没问题”当结论** —— 未经实跑验证的推演必须明确标注为“假设”。
- **禁止把宿主机和容器的测试结果混排对比** —— 两套环境依赖与资源不同，数字不可直接比较。
- **禁止只写分支名不写 SHA** —— 分支指针会移动，脱离 SHA 的结论无法回溯。
- **禁止用活库的行数或时间戳绝对值当判据** —— 共享数据随时变化，应改用 ID 差集、内容哈希等稳定指标。
- **禁止用恒等变换当主判据** —— 对同一对象算两次哈希等恒真比对只能作辅助防伪说明。
- **禁止凭猜测写“这是 XX 的提交/改动”** —— 归属判断必须遵循 5.2 节规则。

## 5.2 交接验收与“提交归属”判断规则

### 把改动交给别人验收
- 交接时同时提供 **分支名 + 具体 SHA**。
- 验收方应使用 `git worktree add --detach "$WT" <sha>` 在自己的独立 `worktree` 中检出验证，不要直接在开发分支上检出。
- 验收结论必须绑定 SHA（如：“已在 `a1b2c3d` 上验证通过”）。

### 如何判断“某个提交或改动是谁做的”

在多 Agent 共享主机或仓库的场景下，要确认某个提交是谁做的，**唯一可靠的依据是：对方汇报时明确给出的 SHA + `git reflog` + 会话/工具调用日志**。

以下四个常见字段对“是谁做的”**信息量为零**，正反两个方向均不成立（既不能用来证明是某人做的，也不能用来排除是某人做的）：

| 字段 | 为什么不能用来判断归属 |
|---|---|
| `author` / `committer` | 多个 Agent 常共用同一台机器的全局 Git 配置或同一个账号；或者同一个人存在多种拼写格式。 |
| `worktree` 目录名 | 只代表目录最初创建时的命名。目录可能被其他任务借用，里面也可能随时检出别人的分支。 |
| 分支名前缀 | 如 `alice/fix-x`，可能是历史遗留分支，也可能是问题提出人而非实际编写人。 |
| 提交时间戳 | 只能说明提交发生的时刻；多个 Agent 并行工作时，同一分钟内完全可能有多个不同来源的提交。 |

**归属判断实践准则**：
1. **需要确认归属时，直接询问或查会话记录**，不要从上述四个字段里福尔摩斯式猜谜。
2. **汇报时只认 SHA**：写“提交 `<sha>` 修改了……”，不要写“XX 的提交修改了……”，一旦张冠李戴会被后续流程一路传错。
3. **不要用 Git `author` 做工作量统计或追责**：在共用环境的多 Agent 体系下，这条路径天然走不通。
4. **当别人拿着一条提交问你“这是谁改的”而你只有 `author` 信息时，直接回答“仅凭 Git 记录无法确定，需查会话记录或对应 SHA”**——实事求是地说不知道是正确答案，强行猜一个名字才是失职。

## 5.3 收尾清理

任务合并或验收完毕后，及时清理临时 `worktree` 与不再需要的临时容器：

```bash
git -C "$REPO" worktree remove "$WT"     # 确认无有用未提交改动时可加 --force
git -C "$REPO" worktree prune            # 每次收尾顺手 prune，清除失效记录
git -C "$REPO" worktree list             # 检查剩余列表
```

- **每个任务收尾就执行一次 `git worktree prune`**：不要积攒。积攒几十个失效目录后，`git worktree list` 会混杂大量 `prunable` 记录，肉眼极易看错行（若已经积攒较多，改用 `git worktree list --porcelain` 过滤）。
- **容器按 `note` 决定去留**：一次性临时容器用完销毁；若容器已配好通用依赖且写明了 `note` 供后续复用，保留容器本身（仅清理里面的残留测试进程与临时文件），不要误删他人或公共注明复用的容器。
- **删目录不等于丢结论**：测试结论绑定的是 SHA 和环境参数，清理临时目录是完全安全的；但**尚未合并的实验分支不要删除**，保留其 SHA 供后续回溯。

# 常见反模式速查表

| 阶段 | 反模式（错误做法） | 导致的后果 |
|---|---|---|
| **1. 开工与工作区** | 基于分支开发时，不现场 `rev-parse` 而直接照抄旧对话里的过期 SHA（或反过来，要求基于固定 commit 时擅自拉最新） | 基线与需求错位，改动落在错误节点上，后续差异比对全部失真 |
| | 在主工作区直接 `checkout` 分支做实验 | 直接打断其他 Agent，导致对方测试结果与代码对不上 |
| | 把 `worktree` 建在主仓库目录内部 | 被主仓库 `git status` 当成未跟踪文件，极易被别人误提交 |
| | 用 `git stash` 临时保存修改 | `stash` 全仓库共享，会被别人看到甚至误 `pop` 覆盖 |
| | 用 `checkout -- .` / `restore` / `stash` / `clean` 清理共享工作区 | 全目录无差别抹除，直接删掉其他 Agent 几小时的未提交工作且不可恢复 |
| **2. 环境与并发** | 两个 Agent 同时启动服务争抢同一固定端口 | 测试随机报错，且双方都误以为是自己代码写错了 |
| | 不看已有容器 `note` 盲目新建容器，或建完容器不写 `note` | 重复创建环境、重复装包浪费资源；容器列表变成无人敢碰的黑盒 |
| | 只建 `worktree` 不隔离测试环境 | 共用虚拟环境与端口，依赖漂移或端口冲突导致测试结果不可比 |
| | 只隔离容器环境不用独立 `worktree` | 容器挂载同一宿主目录，别人切分支时容器内代码跟着变 |
| | 在容器内调用宿主机虚拟环境的绝对路径 | 路径不存在或二进制不兼容，报错与被测代码无关 |
| | 直接连接真实数据库跑写入测试 | 造成不可逆的数据污染，或因抢占写锁导致活库故障 |
| **3. 测试与判据** | 只在改完代码后跑一次测试，不跑基线 | 把仓库既有的失败算到自己头上，或把自己引入的失败当成既有问题 |
| | 容器内盲目使用 `pytest -n auto` | 按宿主机核数开进程触发容器 CPU 限流/OOM，超时被误判为并发 bug |
| | 判据只看“改动后变绿”，不做变异验证 | 分不清“判据有效”和“判据恒真”，测试可能毫无保护力 |
| | 变异验证只靠读代码脑补，不实际跑命令 | 脑补只是主观假设，不是客观运行证据 |
| | 用活库的行数或时间戳绝对值做断言判据 | 活库数据持续变化，判据当场失效（应改用 ID 差集或内容哈希） |
| **4. 提交与合并** | 半成品直接提交到 `main` / `dev` 主干 | 主干不可用，阻塞所有并行开发的 Agent |
| | 在共享/主工作区使用 `git add -A` 或 `git add .` | 把别人的未提交半成品或临时文件静默打包进自己的 commit |
| | 用 `git checkout --theirs .` / `--ours .` 整片解决冲突 | 对方或自己的整片代码被静默丢弃，难以察觉 |
| **5. 交付与归属** | 汇报只写分支名，不写具体 SHA | 分支前进后结论无法复现，验收失去基准 |
| | 凭 `author`、`worktree` 目录名、分支名前缀指认提交人 | 这些字段对归属判断信息量为零，正反方向均不成立，猜错后一路传错 |
